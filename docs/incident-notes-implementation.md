# Incident notes implementation

Incident readers can inspect current notes and their retained revision/deletion history. Editors can add, edit, or delete any note on an active or resolved incident. The notes panel preserves a draft's incident revision across refreshes and tab changes, requires explicit deletion confirmation, and retains the original command UUID, payload, and DELETE headers after an uncertain outcome. A conflict preserves the draft until the user reviews current text and discards/reopens it; a current authorization failure refreshes the session and removes write controls.

`GET /api/tenants/{tenant_id}/incidents/{incident_id}/notes` returns the parent incident revision in `meta.revision`, coherently read with the page while holding identity and incident shared locks. `include_deleted=true` is an optional discovery filter: deleted rows have `text: null` and provide a history target, never a deleted body presented as current text. The default current list and search continue to exclude deleted notes. The opaque cursor binds this filter.

`GET /api/tenants/{tenant_id}/incidents/{incident_id}/notes/{note_id}/history` returns revisions newest first, with text, deletion marker, actor UUID, captured actor display name, and recording time. Default page size is 50, maximum 200. The first page captures the highest serialized note revision as an immutable recording watermark. Later pages keep that watermark and the original 15-minute cursor expiry; every request reauthorizes and checks the retained parent. Cursors bind tenant, incident, note, actor/session, ordering, and deployment epoch. Historical and deleted text is rendered as escaped plain text, with deletion events explicitly distinguished from current content.

Migration `0028_incident_note_history.sql` adds the captured author label and paging indexes. New note mutations capture the trusted author display name inside the authorization transaction. Existing rows remain null because a current LDAP name cannot establish a historical name; the UI reports that the historical name is unavailable. No inferred historical label is backfilled.

Verification uses synthetic authenticated fixtures against an isolated PostgreSQL database under the restricted `appchi_api` role. Five integration cases cover coherent concurrent reads, parent versus note revisions, resolved edit/no-op/delete and idempotency, retained author snapshots, upper watermark paging, deleted-body separation, cursor scope/tamper/expiry, current access loss and retired parents. Browser tests use mocked API responses, separately from PostgreSQL evidence, and cover edit/create/delete retries, conflicts, permission loss, plain-text history, deleted-note discovery and removal of stale history after parent retirement. These are local implementation checks, not company identity or deployment qualification.
